# Add a tester for another 42 project

Use this skill when extending **ftorture itself**, not when testing a student's project. A new project needs integration throughout the runner; adding a `TEST` macro alone will not make it selectable. First read the exact 42 subject/version and the existing implementations in `torture.sh`, `checks.sh`, `gnl.sh`, `src/engine.c`, `src/project.h`, `src/zft.h`, and the closest `src/<project>/` directory. Do not assume libft's archive, Makefile, allowed symbols, or reference functions apply to the new subject.

## Design and integration

1. Record mandatory/bonus deliverables, prototypes, compiler flags, allowed external functions, undefined behavior, resource limits, and expected exit behavior **from the subject**. Keep mandatory and bonus checks separate. Specify when a warning is speculative instead of required.
2. Add project detection, CLI aliases, interactive selection, directory validation, build strategy, checks, and part/bonus selection to the shell runner. Follow the archive-based `torture.sh` path for Makefile projects or the source-based `gnl.sh` path when the subject has no Makefile. Resolve all paths relative to the ftorture checkout; write tester artifacts to `build/<project>/`, not the student's repository. Do not delete user files outside the project's documented build/cleanup rules.
3. Define exactly one `g_proj` descriptor for that tester executable in `src/<project>/proj.c` (see `src/project.h`). Give each suite a stable key, display label, part number, and function address; weak declarations allow a missing student symbol to be reported rather than crashing during link. Add subject-derived prototypes to `protos/<project>.txt` if prototype checks apply; adapt checks instead of copying another project's rules.
4. Link `src/engine.c`, `src/memtrack.c`, the new suite sources, and student sources/archive with the necessary include paths, plus `-lm` (the efficiency summary uses `log`/`exp`). Existing suites use `-Wl,--wrap=malloc -Wl,--wrap=free`; add other wrappers only when justified by the subject. `link_tester` globs `src/<project>/*.c`; `gnl.sh` lists its sources explicitly, so a new file there must be added to `tests=(…)`. Preserve the runner's report, log, exit-status, cleanup, and mandatory/bonus behavior.
5. Shared checks live in `checks.sh` (sourced by `torture.sh`, used by `gnl.sh`): `check_files` (extra files, KO) and `check_includes` (unused `#include`, KO). A new project **must** extend `allowed_path` with its deliverables, or every file is reported as extra. Both scans go through `hidden_prune` so `--no-hidden` (`IGNORE_HIDDEN=1`) keeps working; do not add another `find` without it. Run `check_files` after `make fclean` and before building. Keep shell scripts bash 4+ (`mapfile -d`), and remember that `local a=… b="$a"` expands `$a` before it is assigned.
6. User-facing French strings of the shell are translated by `tr_text` in `locale.sh` (`from|to`, applied in order, plain substring replacement). Put a longer phrase **before** any shorter entry it contains (the short `aucun|none` rule is last so `aucune` does not become `nonee`). New engine strings use `L("fr", "en")` in `src/engine.c`.
7. Adding a menu option means updating, in `tui_options`, the `labels` and `vals` arrays, the `for i in …` list, the "launch" index (`sel` start, `[ $sel = N ]`, the `% (N+1)` wrap and `-lt N` tests) and the mapping back to variables, then passing the flag through `PASS+=(…)`. Check it in a pty, not only with `bash -n`.

## Write trustworthy C tests

- Put focused tests in `src/<project>/t_*.c`, using `TEST(suite, "case")`, `SPEC_TEST` only for non-required behavior, `VS`/`VS_SPEC` for a justified reference, and `MTEST` for allocation-failure resilience. Tests register through constructors in `src/zft.h`; suite keys must match the descriptor. The engine forks each run, so communicate comparison values with `OUT(...)` on **both** paths of `VS`, and use `PICK(student_fn, reference_fn)` for reference selection. A reference implementation must be independent of the student code; libc is not a valid oracle for every subject behavior.
- Add `INPUT(...)` before a failure-prone call, then assert with `CHECK`, `EQ_INT`, `EQ_SZ`, `EQ_STR`, or `EQ_MEM`. Compare exact output bytes and return values for output projects (see `src/printf/pf.h`), not just visible text. For size/ownership requirements use `alloc_size`, `gstr`/`gmem`/`gbuf`, and clean up allocations and file descriptors. Use `XFREE` for memory originating from either the student or reference path.
- For `MTEST`, bracket relevant allocations with `ARM()`/`DISARM()`; the engine replays each allocation failure and treats crashes/leaks as errors. Keep randomized cases deterministic with `zrand()` and `--seed`; avoid flaky timing and assumptions beyond the Linux/subject contract. Mark undefined or implementation-dependent cases speculative rather than demanding one arbitrary result.

## Efficiency workloads (`-e`)

- Add `src/<project>/b_*.c` with `BENCH(key) { COST(...); BENCH_LOOP { … } }` (see `src/zft.h`). The key matches a suite key of the descriptor (`ft_strlen`, GNL's `GNL_SUITE`); a key that matches no suite (`ft_printf`) is a project-level benchmark, run once per pass after the suites and labelled ` (bonus)` with `-p 2`. Call the student function directly (no reference implementation). Feed results to `SINK(x)` so nothing is optimised away; build fixtures once with a `static` guard (the first call is a warm-up, and is when `COST()` is read). Free with `free` (malloc is not instrumented during a benchmark).
- `COST()` declares, per repetition, the **minimal** work a perfect implementation cannot avoid, in the `t_cost` units: `iters` (harness loop turns), `calls` and `ops` (priced **on top** of the loop turn they sit in), `scan`/`copy`/`store`/`cmp` bytes (each includes its own loop turn), `digits`, `nodes`, `allocs`, `big_allocs`, `sys`, `rbytes`. Count the harness work inside the loop too (callbacks, the frees of what the student allocated, an `lseek`), but not cheap libc helpers used for setup. It may depend on runtime data (GNL computes it from the file and `Z_BS`). Do not invent work a perfect version would skip (one `write()` per string, not per char; one pass when one is enough), and write the reasoning in a comment above the `BENCH`.
- `hw_calibrate()` in `src/engine.c` prices each unit once per process: tightest `-O0` loop, L1-sized data (`HW_N` 4 KiB, `HW_NODES` 1024), fastest of several loop shapes (index `int`/`size_t`, pointer), best of 20; `calls`/`ops` are measured against an empty loop. When adding a unit, add its field to `t_cost`, a calibration, `ideal_time()`, the debug/log lines, and keep the stats file layout (`g_fs`, `g_ck`, `g_nbr`, `g_br`, `g_hw_ok`, `g_hw`, appended in that order).
- The student side is calibrated to ~15 ms of repetitions in its own process, best time per repetition of 3 runs, killed after 2 s (shown as `<N%`). Check a new workload with `FTORTURE_BENCH_DEBUG=1`: a clean implementation should land near 100% (not far above: that means the `COST()` overcounts), a slow-on-purpose fixture low, and reruns within a few %.

## Memory tracker limits

`memtrack.c` gives every malloc its own guarded mapping in a 131 072-entry table; past 3/4 full it falls back to the real malloc, and after 20 000 frees it `munmap`s blocks (state 3) whose address range the libc may reuse. Tests that make hundreds of thousands of allocations (GNL with `BUFFER_SIZE=1`) exercise this path: keep `is_mapped` checks on state-3 entries, or "free in the middle of a block" / "double free" false positives come back.

## Validate before shipping

Run shell syntax checks (`bash -n torture.sh` and any new shell file), compile the tester, then run focused and full mandatory/bonus suites against a **known-good** implementation and deliberately broken fixtures. Confirm both real failures and missing symbols report correctly; no bonus is reported as skipped, not passed; `-f`/`-p` select the right cases; `-s` affects only speculative verdicts; build/link errors fail clearly; and the student's repository is left with the expected cleanup. Validate checks on a deliberately messy fixture too: unused `<stdio.h>`, a duplicate include, a project header nothing uses, `.py`/`.txt`/`.o`/hidden files and an empty folder must all be KO, while a header used only through its includers stays OK. Update `README.md` and `README.fr.md` with supported subject version, installation/usage, scope, and limitations. Never weaken tests just to make a particular student implementation pass.
